# ClassQuest security baseline

Last updated: 2026-08-22

This folder records small, compatibility-preserving security improvements that have been
implemented and verified. It is intentionally not a claim that the application has completed a
full security audit.

## Added in the upload hardening change

### Server-generated storage names

Uploaded multipart filenames are user-controlled metadata. They are still retained in the
database for display, but they are never used to construct a filesystem path.

Files are now stored under:

```text
uploads/<server-id>/<document-id>
```

Both directory components are generated by the server. This prevents relative traversal names,
absolute paths, platform-specific separators, and filename collisions from changing the storage
destination.

### Bounded upload reads

The backend now reads at most one byte beyond the configured per-file limit. The extra byte is
enough to determine that the upload is oversized without consuming the entire file in application
code. Files at exactly the configured limit continue to be accepted.

The existing protections remain in place:

- authenticated server creation;
- maximum file count;
- maximum extracted character count;
- supported extension allow-list;
- PDF signature check;
- invalid or unreadable document rejection;
- private-server membership checks; and
- owner-only server deletion.

## Regression coverage

The backend tests now prove that:

- `../outside.txt` cannot escape the server upload directory;
- `/tmp/outside.txt` cannot select an absolute storage destination;
- the original client filename remains available as display metadata;
- stored bytes are unchanged;
- the upload reader requests no more than `limit + 1` bytes;
- a file exactly at the configured limit remains valid; and
- the ordinary mixed file-and-pasted-text workflow still works.

## Deliberately deferred

These items require deployment or product decisions and were not added as part of this low-impact
change:

- edge or shared-store rate limiting for login, registration, join codes, and AI generation;
- email verification, password reset, and account deletion;
- short-lived access tokens with refresh or revocation;
- malware scanning or document-parser isolation;
- upload limits enforced by the reverse proxy before multipart parsing; and
- a Content Security Policy coordinated with the deployed API origin.

An in-process rate limiter was intentionally avoided because it would reset on deployment, would
not coordinate across replicas, and could misidentify users when proxy headers are configured
incorrectly. Rate limiting should be enforced at the trusted edge or through a shared store.

## Production checklist

- Set a unique, randomly generated JWT signing secret; never use the development default.
- Restrict CORS to the deployed web origin.
- Keep the data volume private and include the SQLite database and uploads in tested backups.
- Configure request-body limits at the reverse proxy.
- Do not log bearer tokens, passwords, uploaded course text, or model API keys.
- Review dependency advisories before releases that change document parsers.
