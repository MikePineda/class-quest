Good morning. This is the first session where we actually write Python, so I want to set expectations. By the end of the hour you will have seen four things: variables, the types that values come in, how to print, and how to hold a list of things and walk over it. That is genuinely most of what you need to write a useful program. The rest of this unit is depth on those four ideas, not new ideas. I also want to warn you about something. Every one of these four topics has a standard misunderstanding attached to it, and those misunderstandings are not signs that you are bad at this. They are the natural conclusion to draw from the way the syntax looks. I am going to name each one as we go, because a wrong mental model that you never say out loud is the thing that makes week six impossible.

Let us start with variables. A variable is a name bound to a value. When you write count = 5, Python evaluates the right-hand side first, produces the integer 5, and then makes the name count refer to it. Read the equals sign as "gets" or "is now bound to", never as "equals". This matters more than it sounds. In mathematics, x = x + 1 is a false statement with no solutions. In Python, count = count + 1 is a perfectly ordinary instruction: work out what count is now, add one, and bind the name to that new value. The single equals sign is an instruction, not a claim. When we get to comparisons in a moment you will meet the double equals sign, and that one is the claim. Beginners write if x = 5 constantly, and Python refuses to run the file at all, which is a kindness.

The other thing to know about names is that rebinding one does not disturb anything else. If you write a = 3, then b = a, then a = 10, the value of b is still 3. The line b = a copied the reference to the value 3 into b; it did not tie b to a. There is no permanent link between two names just because one was assigned from the other. Students often expect b to follow a around, as though the assignment set up a relationship. It did not. Each assignment is a single moment, and after it the two names go their separate ways.

Now, types. Every value in Python is of some type, and the type determines what the value can do. The four you will meet today are int for whole numbers, float for numbers with a decimal point, str for text, and bool for True and False. You can ask any value what it is with the type function. The important consequence is that the same operator can mean different things depending on the types it is given. The plus sign adds two numbers, but it joins two strings end to end. So 2 + 3 is 5, and "2" + "3" is the string "23". Neither of these is a special case; both are just what plus means for that type.

This leads directly to the misunderstanding I want to name. Quotation marks are not decoration. The value 5 and the value "5" are different values of different types, and Python will not quietly convert between them. Writing "5" + 5 does not produce 10 and it does not produce "55". It raises a TypeError, because you have asked Python to decide whether plus means arithmetic or joining, and it refuses to guess. This comes up constantly the first time you read something a user typed, because input always hands you a string, even when the user typed digits. If you want the number, you have to ask for it: int(answer) turns the string "5" into the integer 5. Converting is a thing you do deliberately, and forgetting to is probably the single most common error in a first Python program.

Printing is next, and it is where the smallest misunderstanding causes the most confusion later. The print function displays a value on the screen. That is all it does. It shows something to a human being. What print does not do is give the value back to your program. Writing result = print("hello") does not put the string "hello" into result. It puts None into result, because None is what print hands back, and the word hello appears on the screen as a side effect. Displaying and returning are two completely different things, and print only does the first.

I labour this because of how you will debug. When you are working in a notebook or the interactive prompt, the prompt echoes the value of whatever you type, so print appears to be optional and appears to be the same as producing a value. In a real script it is not. A function that prints its answer instead of returning it is a function whose answer nobody else can use. When you start writing functions in a fortnight, this distinction is the one that will bite, and it will look like your code is working because you can see the right number on the screen.

Right, lists. A list holds several values in order, written inside square brackets and separated by commas. So scores = [90, 85, 100] is a list of three integers. Order is part of the list: [1, 2] and [2, 1] are different lists. A list can hold values of different types, and it can hold other lists, though a list where every item means the same kind of thing is usually a list you can actually work with. You get the number of items with the len function, so len(scores) is 3, and you add an item on the end with scores.append(70).

To get one item out you use its index in square brackets, and here is the thing everyone trips over. Indexing starts at zero. The first item of scores is scores[0], the second is scores[1], and the third is scores[2]. There is no scores[3]; asking for it raises an IndexError. So for a list of length three, the valid indexes are 0, 1 and 2 — the last index is always one less than the length. This feels arbitrary for about a week and then becomes invisible. The useful shortcut is that scores[-1] is the last item, scores[-2] the one before it, counting from the end, which saves you writing len(scores) - 1 everywhere.

Finally, loops. A for loop runs the same block of code once for each item in a sequence. When you write for score in scores, Python takes the first item of the list, binds the name score to it, runs the indented block, then takes the second item, rebinds score, runs the block again, and so on until the list is exhausted. The loop variable is an ordinary name being rebound each time round; there is nothing magic about it. Notice that this walks over the items themselves, not over their positions. If you want the positions as well, enumerate gives you both.

You will also see for i in range(n), which counts. This is where the second big off-by-one lives. The range function stops before the number you give it, so range(3) produces 0, 1 and 2 — three numbers, but never 3 itself. That is not a quirk to memorise separately; it is the same convention as indexing, and the two are designed to fit together, which is why range(len(scores)) gives exactly the valid indexes of the list. Students very reasonably read range(3) as "up to and including three", and then their loop misses the last item or runs off the end.

One last warning, and then the exercise. Do not add items to a list or remove them from it while you are looping over that same list. The loop tracks its position by number, so removing an item shifts everything after it down by one and the loop skips the next one; appending inside the loop can make it run forever. Build a new list instead and use that. For the exercise: write a program that holds a list of five test scores, prints each one on its own line with its position, and then prints the average. Use a for loop, use len, and do not use anything we have not covered. Bring your errors to the lab, because reading a traceback is the actual skill.
